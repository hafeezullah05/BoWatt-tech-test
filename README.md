# BoWatt Case Study — Research Agent

A research agent with a React frontend and a FastAPI backend. The user submits a research
question, optionally uploads source files, and the backend retrieves relevant content from
those sources (if any) and streams back a markdown answer generated by Claude.

## Project status

This project is being built incrementally. Currently working:

- Frontend UI (provided).
- `POST /api/research` — streams a Claude-generated answer back to the frontend in real time.
- `POST /api/sources` — accepts uploaded `.txt`-style files, chunks them, embeds them locally,
  and stores them in a persistent Chroma vector store.
- Retrieval-augmented generation: before answering, the backend embeds the user's question,
  retrieves the most relevant stored chunks (if any), and includes them as context for Claude.
- Basic error handling: empty requests and empty upload batches are rejected with clear HTTP
  errors; a non-UTF-8 file no longer fails an entire upload batch; retrieval failures fall back
  to answering without context instead of failing the request; Claude API failures during
  streaming return a readable error message instead of crashing the connection.
- Concurrency: multiple uploaded files are processed in parallel, and blocking calls
  (embedding, vector search) run in a thread pool so they don't block the server's event loop.

Not yet built:

- A web-search tool so the agent can use external sources (currently answers only from Claude's
  own knowledge plus whatever has been uploaded — no live internet lookup).
- A true tool-calling agent loop (Claude currently doesn't decide when to retrieve/search; the
  backend always retrieves once, then generates).
- Tests.
- Several smaller edge cases are intentionally deferred and marked with `# TODO:` comments in
  the code — e.g. no file-size limits, no upload deduplication, no relevance threshold on
  retrieved chunks, no system prompt, hardcoded `max_tokens`.

## Prerequisites

- Python 3.11
- Node.js (for the frontend)
- An [Anthropic API key](https://console.anthropic.com)
- A [Tavily API key](https://tavily.com) (for the planned web-search tool; not required yet)

## Setup

### Backend

1. Create and activate a dedicated environment (conda example — a plain `venv` works too):

   ```bash
   conda create -n bowatt-backend python=3.11 -y
   conda activate bowatt-backend
   ```

2. Install dependencies:

   ```bash
   cd backend
   pip install -r requirements.txt
   ```

3. Create your local environment file and fill in your real API keys:

   ```bash
   cp .env.example .env
   ```

   Edit `backend/.env` and set `ANTHROPIC_API_KEY` and `TAVILY_API_KEY` to your real keys.

### Frontend

```bash
cd frontend
npm install
```

## Running the project

Run each of these in its own terminal tab, from the project root.

**Backend:**

```bash
cd backend
conda activate bowatt-backend
uvicorn main:app --reload --port 8787
```

**Frontend:**

```bash
cd frontend
npm run dev
```

Then open the URL Vite prints (usually `http://localhost:5173`) in your browser.

## Trying it out

1. Upload a plain text file under "Your sources" containing some information Claude wouldn't
   otherwise know (e.g. a made-up fact, or specific figures from an internal document).
2. Ask a research question about that specific content.
3. The streamed answer should reflect the uploaded content, not just general knowledge — this
   confirms retrieval is working, not just the Claude passthrough.
4. Ask a general question with nothing relevant uploaded (e.g. "What is a neural network?") to
   see it fall back to Claude's own knowledge.

## Project structure

```
backend/
  main.py                    # FastAPI app entrypoint, CORS setup
  rest/
    router.py                 # HTTP endpoints: POST /api/research, POST /api/sources
  app/
    config.py                 # typed settings loaded from .env
    schemas.py                  # request/response models
    agent/
      research_agent.py         # retrieval + streams a Claude-generated answer
    ingestion/
      chunking.py                # splits uploaded text into overlapping chunks
      embeddings.py                # local sentence-transformers embedding model
      vector_store.py               # Chroma persistent vector store (add/query)
frontend/                        # provided React + Vite UI
```

## Architecture and design decisions

I built this as a fairly small, linear pipeline rather than a full agent framework, mostly
because I wanted something I could reason about end to end and actually get working, rather
than something that looks impressive on paper but I can't fully explain.

**Why FastAPI.** I needed real streaming (the frontend reads the response body as it arrives),
and FastAPI's `StreamingResponse` plus native `async`/`await` made that straightforward. It's
also just a natural fit for anything ML-adjacent in Python.

**Why Claude for the agent, and a local model for embeddings.** I had an Anthropic key
available, so Claude does the actual reasoning/generation. Anthropic doesn't offer an
embeddings endpoint though, so for turning text into vectors I used a small local model
(`sentence-transformers`, specifically `all-MiniLM-L6-v2`) instead of pulling in a second paid
API just for that. It's not as strong as a hosted embeddings API, but it's free, fast enough for
this scale, and means the whole ingestion pipeline works offline once the model is cached.

**Why Chroma.** I wanted a vector store I could run locally with zero setup — no server to
stand up, no account to create. Chroma persists to a local folder on disk, which is enough for
a project like this. It would not be my choice for anything that needs to scale past a single
machine.

**How a request actually flows, end to end:**

1. A user uploads a file → the backend reads it as text, splits it into overlapping ~200-word
   chunks along sentence boundaries (so a chunk never cuts a sentence in half), embeds each
   chunk, and stores the chunks and their vectors in Chroma.
2. A user asks a question → the backend embeds the question the same way, asks Chroma for the
   most similar stored chunks, and if it finds any, stuffs them into the prompt as context.
3. That prompt (question, plus context if any) goes to Claude, and the answer streams back to
   the frontend token by token as it's generated.

That's genuinely it — there's no agent "deciding" anything right now. It's closer to a fixed
retrieve-then-generate pipeline than a true agent. I'm calling that out honestly rather than
overselling it, because it matters for what's still missing (see below).

**A decision I want to be upfront about:** I did not get to building the web-search tool, which
means the "the agent should be able to utilise external sources" requirement isn't done. If I'd
had more time, I would have added a `search_web` tool (using Tavily) and switched the agent
from "always retrieve once, then generate" into a real Claude tool-calling loop, where Claude
itself decides whether it needs to search the knowledge base, search the web, both, or neither,
before answering. That's a meaningfully bigger and riskier piece of work to get right (handling
tool-use messages, running tools concurrently, feeding results back, looping until Claude is
done), and I'd rather ship a smaller thing that actually works than a half-finished version of
the bigger thing.

**Other things I knowingly cut for time**, each marked with a `# TODO:` comment at the relevant
spot in the code: no relevance threshold on retrieval (so an irrelevant stored chunk can still
get pulled in once anything has been uploaded), no deduplication on re-uploading the same file,
no file size/count limits, no system prompt telling Claude how to behave as a research agent,
and a hardcoded `max_tokens` that could silently cut off a long answer.

## Example queries and expected outputs

**Query with no sources uploaded:**
> "What is a neural network?"

Expected: a general, correct explanation, coming entirely from Claude's own training — nothing
retrieved, since there's nothing in the store to retrieve.

**Query after uploading a source file containing information Claude couldn't otherwise know**
(I tested this with a text file describing a made-up project, "Project Zephyrine-9," with
invented facts like a 94.7% recovery rate and a made-up inventor):

> "What is Project Zephyrine-9 and what recovery rate does it achieve?"

Expected: the answer includes those specific invented details (the name, the percentage, the
people mentioned in the file). If it does, that's proof the answer came from the uploaded file
and not from Claude just guessing — there's no other way it could know a fact I made up myself.
This is the actual test I ran to confirm retrieval was working, not just assumed.

**Query about something unrelated to any uploaded source:**

Right now, if you've uploaded something but ask about a completely different topic, the backend
still retrieves and injects whatever chunks are "closest" in the store, even if they're not
actually relevant — there's no similarity cutoff yet. In practice Claude is usually good at
noticing irrelevant context and ignoring it, but that's Claude compensating for a gap in my
retrieval logic, not something I've actually built and can guarantee. I've left this as a
documented limitation rather than pretending it's solved.

## How I'd evaluate this agent, and why

The honest answer is: right now I have no automated way to measure whether an answer is good,
only my own manual spot-checking (like the Zephyrine-9 test above). If I were going to keep
improving this, here's what I'd actually build, in order of what I think matters most:

**1. Faithfulness (does the answer actually match the retrieved context, or did it make
something up?).** This is the most important thing to measure for a RAG system specifically,
because the whole point of retrieval is to ground the answer in real source material. My plan
would be to build a small set of test questions where I know the "correct" answer from the
source file, then use a second LLM call as a judge: give it the retrieved context and the
generated answer, and ask it to score whether every claim in the answer is actually supported
by the context. This is the standard "LLM-as-judge" approach used by evaluation frameworks like
RAGAS, and it's practical to build without needing a large hand-labeled dataset.

**2. Hallucination rate.** Closely related to faithfulness, but I'd track it separately and
specifically for the no-context case — i.e., when nothing relevant was retrieved, does the
agent clearly say it doesn't know, or does it confidently invent an answer? I'd build a small
set of questions I know have no answer in any uploaded source, and check how often the agent
states uncertainty versus fabricates something plausible-sounding.

**3. Retrieval quality, separately from generation quality.** Right now if an answer is wrong,
I can't tell whether that's because retrieval pulled the wrong chunks, or because Claude
misused the right chunks. I'd want a way to check retrieval on its own — e.g. for a known
question/source pair, did the correct chunk actually show up in the top-N results at all? This
would also be where I'd validate whether adding a similarity threshold (mentioned above as a
known gap) actually helps or just makes recall worse.

**4. Basic user-facing quality signals**, further out: response latency (time to first token,
since streaming makes perceived speed matter a lot), and eventually real user feedback
(thumbs up/down on answers) if this were a real product rather than a test project.

Why this order: faithfulness and hallucination are the risks that are actually dangerous in a
research tool — a confident, wrong answer is worse than a slow one. Retrieval quality is the
lever I'd actually pull to fix those problems once I could measure them. Everything else is
secondary polish.

## What I'd do next, if I kept working on this

- Build the `search_web` tool (Tavily) and the real tool-calling agent loop, as described above
  — this is the biggest remaining gap against the brief.
- Add the evaluation approach above as an actual runnable script, not just a description.
- Add a similarity/relevance threshold to retrieval instead of always returning the top-N.
- Write unit tests for the pieces that don't need a live API key (chunking, prompt building).
- Containerize with Docker so setup isn't dependent on my local Python/conda environment.
- Add basic upload queueing so large or many files don't block on each other unnecessarily.
